# Architecture and operational behavior

The existing `extensions` repository owns the admin UI, database migrations and a single Supabase Edge Function, `gptyar-api`. Website changes live in `gptyar-web.github.io`; imported extension source and packaging live in `chatgpt`. GitHub Pages only serves public files. No browser can directly query a management table.

## Data and security

All application tables and RPCs use the `gptyar_` prefix in `public` so GPT Yar can share a Supabase project with an existing application. The database adapter keeps logical table names and aliases embedded relations back to their existing UI response keys. No grants, policies or functions belonging to other applications are changed.

Twenty-five application tables hold sessions, encrypted settings, customers, conversations, products, prices, orders, payments, independent payment receipts, subscriptions, operations, discounts/redemptions, videos, versions, audit/events, updates, jobs, limits, leases, ownership claims, upload tickets and replay IDs. Every table has RLS and explicit revocation from `PUBLIC`, `anon` and `authenticated`. Application functions use invoker rights, fixed empty search paths, and execute grants only to `service_role`. Private Storage buckets have no browser write policy; exact-path signed upload capabilities are issued only after admin authentication.

Secrets are encrypted with AES-256-GCM, fresh 96-bit IVs and purpose-bound additional authenticated data. `GPTYAR_ENCRYPTION_KEY` is a 32-byte base64 Edge Function secret, held outside PostgreSQL. Backups of this key must be kept outside the database; losing it prevents decryption. Key rotation requires re-encryption of existing ciphertext, not merely replacing the environment value. API/bot/provider credential rotation is supported in the panel. After replacing a possibly exposed GPT Yar admin token, revoke it with the upstream provider too; deleting local automation permission cannot revoke an upstream token.

Admin login is token-only. Backend validates management capability on **every** protected request. Session bearers are random, stored as SHA-256 in PostgreSQL, kept only in page memory, expire in 8 hours and are revoked on logout. Raw admin credentials are encrypted per session. Automated provisioning requires separate, recorded storage consent in the settings screen. Account scope is pinned at initial setup. Mutations require an authenticated session, exact allowed Origin and unique UUID request ID; repeated request IDs are rejected. Login has transactional global/IP/token limits. The handler never returns raw upstream errors or secret logs.

Bale documents a webhook URL but no authenticated signature/secret-header parameter. The implementation therefore uses a distinct 256-bit random URL capability, stores only its hash in nonsecret bot status and encrypts the original capability. It never uses the bot/admin/provider token as this path. The webhook URL and service logs must remain restricted to infrastructure administrators. Rotation of the bot token recreates the capability. Only private messages whose chat ID equals sender ID are accepted; forwarded/chat identities cannot establish subscription ownership.

## Money, time and state

All monetary amounts are integer IRR. Initial daily/monthly rates exist only in the migration (350000/10000000); the database is the source for bot and website. One month is exactly 30 UTC days, disclosed in bot and website. Renewals add to `max(now, actual upstream expiry)`. UI dates use Persian formatting and Tehran time. Daily reports use Tehran boundaries; the monthly metric explicitly labels a Gregorian calendar month.

Invoice snapshots expire after 20 minutes. Discount limits and capacity reservations use transactional locks. Redemptions remain held for pending/uncertain transactions. Discounts are capped at subtotal minus 1 rial because this invoice flow requires a positive amount; free subscriptions are not issued through the payment path. Changing a price never changes an existing invoice. Cancelling clears unpaid drafts; accepted pre-checkout or paid orders are preserved.

PreCheckout executes on a short path with parallel reads and 700 ms database timeouts, then a 1.8-second Bale reply timeout. It atomically validates invoice ownership, IRR amount, expiry and transaction identity. It does not issue anything. Failed inquiries are persisted. SuccessfulPayment receipts are stored independently and encrypted **before** inquiry. Even unmatched receipts remain visible as `needs_review` without exposing tokens. Final acceptance requires a matched SuccessfulPayment plus `inquireTransaction.status === paid`, transaction ID, `userID` and amount equality.

Wallet saves start disabled and unverified. A 1000-rial probe invoice must be explicitly requested in the panel; in live mode this really charges 1000 rials. The probe never issues a subscription. Only its actual receipt/inquiry can validate the live wallet. Provider revision is frozen into each order; an old payment cannot validate a newly replaced provider. Test invoices use Bale's documented `WALLET-TEST-1111111111111111`, cause no transfer, and can never create or renew a real subscription. Probe and test amounts do not count as sales.

## Crash recovery

Webhook ingestion commits a unique update ID and outbox job in one PostgreSQL function. A global leased worker serializes conversation/provisioning work and claims jobs using `FOR UPDATE SKIP LOCKED`. Job execution may be retried after a crash; retry and error state are durable. A pg_cron invocation every minute is the reliability mechanism. `EdgeRuntime.waitUntil` only lowers latency. Bot activation is blocked if the persistent worker has not run recently.

A purchase writes an operation with a unique `[GY:<order UUID>]` marker and absolute expiry before calling GPT Yar. After an ambiguous create response, the worker searches the upstream subscriber list for that exact marker and never blindly creates a second account. If reconciliation is inconclusive it retains the paid order as `needs_review`. Admin retry performs the same reconciliation. A renewal freezes its target expiry; repeating the absolute update does not add duration twice. Orders without a successful verified live payment cannot reach the database completion function.

Customer names are requested after verified payment. A paid order survives /start, browser closure and server restart. The token delivered is the upstream token, encrypted at rest, sent only to the mapped private Bale customer. Message delivery is at least once; a lost HTTP acknowledgement can resend the same token to the same owner, but cannot issue another subscription.

Old subscriptions require a private token submission and independent admin confirmation of purchase/ownership history; possession of a token alone is not an automatic claim. Existing ownership cannot be overwritten.

Refunds use manual provider-supported handling and a transaction reference. The public Bale Bot API reviewed here does not document a callable refund method, so no invented endpoint is used. The panel records an actual completed refund only for a paid `needs_review` order. Fulfillment reconciliation failures are visible in the dashboard and event log; an optional private Bale alert channel can be paired in settings using a one-time 15-minute link opened by the administrator. Fulfillment errors enqueue a deduplicated notice with order ID and error code; no customer or admin token is included. No external destination is preconfigured.

## Files and releases

Videos/posters use unique immutable paths in private Storage. The public catalog returns signed URLs only for active videos. MP4/WebM is played in native HTML5 video with seeking, volume, fullscreen and inline mobile support. Actual tutorial content must be uploaded with appropriate rights; no external video was downloaded or republished.

ZIP validation bounds compressed/uncompressed size, rejects traversal/encryption/symlinks/duplicate paths, verifies decompression/CRC, checks Manifest V3/version and referenced files, and stores SHA-256. Publication is atomic, previous versions remain available, and rollback is explicit. Publication also requires a recognizable managed update wrapper configured for this exact backend; legacy packages can be archived but cannot silently replace the managed channel. An optional external download host needs an initial allowlist and matching file hash; Storage download links are the default. The source API remains externally controlled. The first managed package requires one-time endpoint packaging and manual installation; subsequent releases are administered in the panel.
